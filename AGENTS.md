# Agent Notes for Cranamp

- Start a skin boundary inspection with `studio_study {rect:[x,y,w,h],states:true}`: it returns native and enlarged four-state editor crops with four pixels of context and source/runtime coverage in one read-only call. Inspect overlapping control cells as well as the background. The GUI Pixel Study follows the live composition; clipboard pixels are separate. Use the actual GPU preview before approving the artwork.

- Before declaring any Skin Studio region inaccessible or leaving a blank for runtime content, inspect the exact native rectangle with `studio_coverage` or `studio_pixel` and review its source targets. Runtime footprints are overlays, not exclusion masks: surrounding and underlying bitmap pixels may be painted. Distinguish actual palette-only playlist fill from editable backgrounds, control cells and footer margins; verify the result in the GPU player and alternate states.

- For annotated skin corrections, preserve the annotated project and map every marked area to an explicit native rectangle before painting. Use `tools/skin-studio/region_review.mjs` with a region manifest to capture before/after editor crops, a 4-pixel exterior halo, ownership, and all four GPU states. Visually inspect every crop and complete overlapping sprites (including menu buttons, MONO/STEREO and repeated rails), not just the full canvas. Mapping counts and passing tests are not visual approval. Do not call a boundary fixed while another sprite still reinstates its old rectangular background.

- Keep all tests, test helpers, and fixtures in the root `/test/` directory. Never write `#[test]` functions, inline test modules, or test-only helpers in implementation files under `src/`. Rust unit tests may retain a `#[cfg(test)]` and `#[path = ".../test/..."]` external module declaration beside the implementation to access private items. Register integration test targets in `Cargo.toml`; put web and platform tests under `/test/` too.

- Do every refactoring, code search, code analysis and code edit through the RustRover MCP (`mcp__rustrover__*`), never with grep, sed, Python heredoc scripts or hand edits for those jobs: `rename_refactoring` for renames, `apply_patch` and `create_new_file` for edits, `search_symbol`, `get_symbol_info` and `analyze_calls` for declarations, usages and call graphs (the IDE knows the code; a regex over its text does not, so `search_text` and `search_regex` are for strings and comments only), `get_file_problems`, `lint_files` and `run_inspection_kts` for analysis, `reformat_file` for formatting; for text searches run `scripts/dev/ide_search.py text|regex|symbol|file <query> [--in <glob>]... [--context N]` from the project root, which asks the same IDE server and prints each hit as path, line and matched text. Pass `projectPath` on every call; when the tools are missing, open the tree in RustRover first (`open -a RustRover <path>`), and say so before any fallback. Bash is for building, testing and git.
